# 07 · 项目迭代叙事

> 这是面试时**讲项目的核心稿**。把项目讲成"我遇到了什么问题 → 我怎么发现的 → 我怎么解决的"，比堆砌技术词更打动人。

## 一、4-5 分钟讲解结构（STAR）

### 起手式（30 秒）

> "这是一个医疗诊断 Agent 系统，核心场景是：用户描述症状，系统结合知识图谱做鉴别诊断、给出可能病因和就医建议。
> 
> 项目最有意思的地方不是'用了什么技术'，而是**每一版架构都是因为前一版踩了坑**。所以我想分四个阶段讲，每个阶段说一个我学到的东西。"

### 阶段 1：基线 RAG（识别问题）

> "v1 是最朴素的：Qwen2.5-7B 做 LoRA 微调（用 Huatuo 15 万问答对），加传统 chunk RAG 检索医学文档。
> 
> 跑在自建的 100 题鉴别诊断集上，准确率只有 52%。
> 
> **关键观察**：错误几乎都集中在多症状鉴别诊断上。比如'头痛+发烧+颈强直可能是什么病'——chunk RAG 检索到'头痛'就召回头痛科普 chunk，模型根本看不到'脑膜炎'这个跨多跳的答案。"

**金句**：
> "这让我意识到：传统 RAG 在医疗多跳推理上有结构性局限。"

### 阶段 2：三 Agent 链式 + 朴素 Reflexion（典型坑）

> "v2 我加了几个东西：
> - 用 Neo4j 构建了 4.5 万实体、31 万关系的医学 KG
> - 三 Agent 架构：思考 Agent → 查询 Agent → 反思 Agent
> - 朴素 Reflexion 做错误修正
> 
> 准确率涨到了 67%。但跑性能测试时发现 **P95 延迟到 9.4 秒**——线上不可用。
> 
> 我做了延迟分解，发现三个问题：
> - 三次独立 LLM 调用，KV Cache 全部失效
> - Reflexion 在所有 query 上无差别触发，简单查询也要走完整反思
> - 多 Agent 间通过 prompt 传状态，信息丢失"

**金句**：
> "这版让我学到一个反直觉的事：**多 Agent 不等于多 LLM**。
> '多 Agent 协作'是说多种角色协作，但最优实现方式是一个 LLM 扮演多个角色 + 多个无状态 Tool。"

### 阶段 3：Planner-Executor + 分级反思（核心改造）

> "v3 是一次大重构。两个核心改动：
> 
> **(1) Planner-Executor 模式**：
> - 一个 LLM Planner 输出结构化 DAG plan，N 个无状态 Tool 并行执行
> - LLM 调用从 3 次降到 1.4 次
> - Self-Critique 在同一 forward 内做，复用 KV Cache
> - DAG 并行 + Speculative Pre-fetch
> 
> **(2) 分级反思**：
> - L1 规则反思（0 LLM，<1ms，拦截 75%）
> - L2 小模型反思（蒸馏 1.5B，~200ms，处理 20%）
> - L3 完整反思（主 7B，~2s，仅 5%）
> 
> 结果：准确率 74%，P95 从 9.4s 降到 3.1s。"

**金句**：
> "最有意思的是 GraphRAG 部分。我没用现成的 Microsoft GraphRAG，而是做了三个领域适配：
> - **PPR 替代邻居召回**：alpha 设为 0.5 而不是常规的 0.85，让 random walker 既能跳出 1-hop 又不会扩散得无意义
> - **三层社区结构**：对应医学的专科-疾病大类-具体疾病
> - **回填验证防幻觉**：摘要中的实体必须在原社区中
> 
> 在多跳 F1 上从 0.21 涨到 0.71。"

### 阶段 4：三层 Memory（系统级飞轮）

> "最后一版加了三层 Memory：
> - **Working**: 会话级，结构化 PatientProfile 注入卡片，token 降 90%
> - **Episodic**: 用户级，Importance Scoring + 混合检索（相似度+重要性+时间衰减+频次）
> - **Semantic**: 全局，L3 反思修正后沉淀回 KG / 规则库
> 
> 重点说一下 Semantic：每次 L3 触发都会做 root cause analysis——
> 是 KG 缺关系？还是缺规则？还是事实错误？
> 然后对应写入 KG、注册新规则、入库失败案例。
> 这就形成了系统级自我进化的闭环。
> 
> 最终多轮一致性从 41% 涨到 88%，过敏冲突拦截率从 23% 涨到 96%。"

**金句**：
> "这一版让我体会到：**Memory 不是 ChatHistory**。
> 三层独立闭环、独立检索时机、独立写入策略，配合 Importance Scoring 和'永不淘汰'机制，是医疗场景下能用的 Memory 系统。"

### 总结（30 秒）

> "整个项目我最大的收获不是某个具体技术，而是**学会用第一性原理去做 Agent 系统**：
> 
> - 朴素 ReAct 慢？不是因为模型慢，是因为 KV Cache 失效
> - Reflexion 贵？不是因为反思贵，是因为无差别全量
> - 多轮记忆不一致？不是因为 ChatHistory 短，是因为没有结构化状态
> 
> 每个改进背后都是 trace 分析 + 定位瓶颈 + 针对性设计。"

## 二、被追问的高频问题

### Q: 你的项目和 LangChain Agent 区别是什么？

A: LangChain Agent 主要是 ReAct 模式，每步都让 LLM 决策。我们的 Planner-Executor 是一次决策一次执行，**LLM 调用次数少 50%+**。另外 LangChain 的 Memory 是单层 ChatHistory，我们是三层独立闭环。架构上是两种不同范式。

### Q: 为什么不用现成的 GraphRAG 框架？

A: 三个理由：
1. **领域适配**：MS GraphRAG 是通用方案，医学多跳推理需要 PPR 这种"自由联想"
2. **可控性**：摘要生成的幻觉问题我们用回填验证解决，框架内不方便改
3. **学习目的**：自己实现一遍才能理解原理，否则面试只会说"用了 GraphRAG"

### Q: 你怎么知道 alpha=0.5 是最优的？

A: 在自建的 100 题多跳集上做网格搜索 [0.3, 0.5, 0.7, 0.85]，看 F1。alpha=0.5 时 F1=0.62，最高。可解释性也合理：太低（0.3）walker 出不去；太高（0.85）扩散过广失去 personalization。

### Q: 三层 Memory 会不会一致性问题？

A: 不会。写入是**单向流动**的：WM → Episodic → Semantic。没有跨层回写，不存在脏写。各层独立时间尺度也避免了同步开销。

### Q: 系统怎么进化？

A: 三个路径：
1. **KG 进化**：L3 反思发现缺关系 → 写入新关系（低 confidence 待审）
2. **规则进化**：L3 发现缺禁忌 → 注册新 L1 规则（带 false positive 反馈机制）
3. **few-shot 进化**：所有 L3 案例入库，下次相似 query 触发 L3 时作为 few-shot

不是模型权重的更新，是知识库 + 规则库的演化。

### Q: 你最想优化的下一步是什么？

A: 三个方向，按优先级：
1. **Planner 蒸馏**：把 Planner 部分蒸馏到 1.5B，对简单查询走快路径，预期 P95 再降 40%
2. **真实部署 Eval**：现在的数据是离线 benchmark，需要小流量上线验证用户感知质量
3. **Tool 自动学习**：现在 Tool 列表是手工设计的，下一步用 ToolBench 思路让系统自动发现需要哪些 Tool

### Q: 这个项目你做了多久？做了哪些部分？

**诚实模板**（务必如实回答）：
> "项目从今年 1 月开始，主体框架 3 月完成，到 6 月做了多版迭代。
> 
> 我个人主要负责：
> - KG 构建：从 Huatuo 数据清洗到 Neo4j 导入和图构建
> - 模型微调：Qwen2.5-7B 在 15 万问答对上做 LoRA 微调
> - 整体架构设计：Planner-Executor + 三层 Memory + 分级反思
> - GraphRAG 模块：社区检测、PPR 实现
> 
> 其中 L2 蒸馏 Verifier 和 GraphRAG 离线索引现在还在迭代中（这点要诚实，面试官追问就答不上来）。"

## 三、避免的几个坑

1. **不要说"全部完整上线"**：大厂面试官会追问具体实现细节，PoC 阶段就说 PoC
2. **不要堆砌名词**：说"用了 LangChain、LlamaIndex、AutoGen、CrewAI"不是优点，是减分项
3. **不要给假数字**：报告时间到秒、准确率到小数后两位但讲不清怎么算的，立即穿帮
4. **不要假装懂所有细节**：被问到 "PPR 在大图上怎么加速" 等不熟的细节，老实说"这个我目前用的是 100 节点子图，全图优化没做过"
5. **不要批评其他方案**：说"LangChain 是垃圾" 显得轻浮。要说"在 X 场景下 LangChain 的 Y 设计有局限"
