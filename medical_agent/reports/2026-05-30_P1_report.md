## 2. 解决的工程问题（面试素材）

### 2.1 社区摘要生成 O(n²) → 700x 加速

**现象**：摘要生成在 45 个社区上耗时 182 秒（平均 4 秒/社区），全量预计十几分钟。

**定位**：摘要本质是字符串拼接，不该这么慢。加计时后定位到两处循环内重复计算：
- `summary_generator.py` 的 `_extract_mentioned_entities`：每次调用都重建+排序
  全局词表（global_terms），而它本该只建一次
- `import_medical_kg.py`：`set(members)` 在内循环里反复重建

**修复**：global_terms 缓存为类属性只建一次；实体查找 list→set；set(members) 提到循环外。

**效果**：182s → 0.27s，约 700x 加速。

**面试一句话**：「把 mock 实现迁到真实规模时，摘要生成出现 O(n²) 瓶颈，
定位到回填验证里的重复全局词表构建，改成缓存 + 哈希查找后从 3 分钟降到 0.3 秒。」

## 4. 已知数据局限（查库验证）

种子"头痛+发烧+颈强直"做 PPR 找不到脑膜炎，经直接查 kg_relations 确认根因如下：

### 4.1 实体粒度不统一（主因）

同一症状在 KG 中有多种表述，字面不同导致边断开：

| 教科书名称 | KG 中的变体 | 影响 |
|-----------|------------|------|
| 头痛 | 剧烈头痛、间歇性头痛、反复发作性头痛、慢性头痛 | "头痛"连 0 个脑膜疾病，"剧烈头痛"连 2 个 |
| 颈强直 | 颈部强硬、颈项强直 | "颈强直"连 7 个脑膜亚型（对齐），"颈部强硬"连 3 个（不对齐） |
| 发烧 | 发热 | "发热"**根本不是 KG 实体**，不存在 |

**关键证据**：脑膜炎亚型（细菌性脑膜炎、真菌性脑膜炎等）确实有"颈强直""发烧""剧烈头痛"等典型症状，但通用词条"脑膜炎"本身的症状列表缺少这些，且症状名与教科书不一致。

### 4.2 通用词条症状稀疏（数据缺口）

"脑膜炎"（总称）只列了 4 个症状：抽搐、新生儿脓漏眼、脑脊液蛋白量增高、食欲不振。
教科书三联征（头痛/发烧/颈强直）的信息分布在亚型上（细菌性脑膜炎→颈强直、肺炎球菌脑膜炎→发烧等），
而不是挂在总称上。

### 4.3 部分症状被错分到 examination 字段

"颈项强直"在 KG 中的类型是 **examination**（检查），不是 symptom（症状）。
"脑膜炎→推荐检查→颈项强直"这条边存在，但关系类型是"推荐检查"而非"典型症状"，
PPR 从症状出发不会走这条边。

### 4.4 处理决策

| 问题 | 决策 | 原因 |
|------|------|------|
| 实体归一化 | **先不做** | 无底洞，边际收益低，发现+根因分析作为工程经验记录即可 |
| 数据缺口 | 接受现状 | 原始数据质量问题，不可人工修补 2.2 万实体 |
| 类型错分 | 不修 | 影响面小，且归一化不做的情况下修单个词条意义不大 |

**工程经验总结**：「真实 KG 接入后，教科书测试用例失败。查库定位到实体粒度不统一
（同一症状多种表述导致边断开）是主因，数据缺口（通用词条症状稀疏）次之。
PPR IDF 算法在 Mock 数据上验证正确，真实数据上的表现受限于数据质量而非算法。
归一化是无底洞暂不做，但这个根因分析本身就是可讲的经验。」

### 5.2 设计决策：diagnoses 从哪抽

**问题**：评测的是什么？——系统给用户的最终回答质量。
原来从工具中间输出提取 diagnoses，但 KG 真实数据上 facts 结构与 mock 不同，导致提取失败。

**两种方案**：
- (a) 让 LLM 在 JSON 里显式输出 `diagnoses` 列表 → 结构化，最可靠
- (b) 从回答文本里匹配 KG 已知 disease 实体名 → 不稳定，依赖 NER/归一化

**选择 (a)**：在 Planner JSON schema 加 `diagnoses` 字段，LLM 直接吐结构化诊断列表。
通过 Plan→FinalAnswer 传递，eval 从 `answer.diagnoses` 提取。L3 reflexion 的
`corrected_answer.possible_diagnoses` 作为备选来源。

## 5c. ✅ 评测指标改进（已完成）

### 主指标调整：F1 → Top-K 命中率

**原因**：CMB-Clin 96% 条目只有单一 gold_diagnoses，F1 测不出鉴别能力。
Top-K 定义：系统输出的诊断候选列表里，gold 是否出现在前 K 个。
报告 Top-1/3/5 命中率（exact 和 loose 两种），F1 作为辅助指标。

**报告说明**：明确注明"CMB-Clin 标注为单一最终诊断，
Top-K 更能反映系统将正确诊断纳入鉴别候选的能力"。

### 宽松匹配规则

**问题**：gold 粒度不一致（如 gold="腹外疝"大类 vs pred="嵌顿性腹股沟斜疝"具体类型），
逐条手修 77 个 gold 是无底洞。

**解决**：在 metrics.py 加 `loose_match` 开关，规则只保留两种命中：

| 匹配类型 | 条件 | 示例 |
|----------|------|------|
| EXACT | pred == gold | "胰腺癌" == "胰腺癌" |
| CONTAINS | pred∈gold 或 gold∈pred | "肠梗阻" ⊂ "嵌顿性腹股沟斜疝合并肠梗阻" |

**关键决策：不放第三种规则**。早期试过"字符集重叠≥2"（如 {腹,疝}），
但导致危险误判："胆管结石" vs "肝左外叶胆管多发结石"（沾边不是答对）、
"胰腺癌" vs "胰腺炎"（共享器官名但完全不同疾病）。
宁可漏判（把对的算错），不要误判（把错的算对）——虚低的数字诚实，虚高的数字面试会穿帮。

**验证**：5 条样本 + 6 条边界测试全部通过：
- "嵌顿性腹股沟斜疝" vs "腹外疝" → MISS（无包含关系，诚实）
- "胆管结石" vs "肝左外叶胆管多发结石" → MISS（不再误判）
- "肠梗阻" ⊂ "嵌顿性腹股沟斜疝合并肠梗阻" → HIT（包含关系）
- "肺癌" vs "胃癌" → MISS（共享"癌"1 字不够）

## 5e. ✅ 系统诊断：PPR 调用率 + Planner 根因 + Memory 噪声（已完成）

V1 评测完成后发现三个异常：PPR 调用率极低、Prefetch hit_rate=0、Verifier 分布偏离设计。
逐一做了根因诊断，不凑数字，只求真实。

### 诊断 1：Planner 工具选择统计

用 `scripts/diagnose_tool_usage.py` 对全部 77 条评测数据直接调用 Planner（不执行工具），统计工具分布：

| 工具 | 被多少条调用 | 占比 |
|------|------------|------|
| ner | 77/77 | 100% |
| kg_local_search | 72/77 | 93.5% |
| kg_global_search | 5/77 | 6.5% |
| ppr_reasoner | 5/77 | 6.5% |

**只有 2 种工具组合模式**：
- `(ner, kg_local_search)` — 72 条 (93.5%)，全部 complexity=medium
- `(ner, kg_global_search, ppr_reasoner)` — 5 条 (6.5%)，全部 complexity=high

PPR 只在 Planner 判定 complexity=high 时被选中，且**总是和 kg_global_search 一起出现**。
Planner 把 PPR 视为 high-complexity 场景的补充工具，而非独立工具。

### 诊断 2：为什么 LLM 不选 PPR——根因定位

Planner 看到的 4 个工具描述：

```
- **ner**: 从用户文本中抽取医疗实体（症状、疾病、药物、时长等）。返回结构化实体列表。
- **kg_local_search**: GraphRAG 实体级检索。适合具体事实查询（如'X 的症状'、'Y 的用法'）。输入: {query: str, entities: Optional[List[str]], max_results: int}。返回: 实体邻居关系列表，按 PageRank 重排。
- **kg_global_search**: GraphRAG 社区级检索。适合需要全局视角的查询（鉴别诊断、可能病因、跨概念推理）。输入: {query: str, focus: Optional[str], top_k: int}。返回: 社区摘要 + 核心实体 + 关键事实。
- **ppr_reasoner**: PPR with IDF weighting and type filtering
```

**根因有两层**：

1. **工具描述问题**（已修）：PPR 原描述是一句简短英文 `"PPR with IDF weighting and type filtering"`，
   其他三个工具都是中文详细描述（含用途、触发条件、输入输出格式）。8B 中文模型看到这句英文，
   不理解它做什么、什么时候该用、怎么传参——自然不选。

2. **复杂度判断瓶颈**（核心问题）：改完描述后重跑诊断，PPR 调用率仍为 6.5%（同样的 5 条）。
   根因是 **Planner 的复杂度判断逻辑**——93.5% 的临床诊断题被判定为 medium 而不是 high。
   Planner prompt 中定义 high=鉴别诊断/多跳推理/安全性判断，但 LLM 在实际推理中把大量鉴别诊断题判为 medium，
   导致只触发 NER+local_search，不触发 PPR 或 global_search。

**PPR 描述修复**：改为中文详细版，对齐其他三个工具的格式：

```
PPR 多跳推理检索。从已知症状/疾病出发，沿知识图谱做 2-hop 扩散，用个性化 PageRank
发现与种子实体有强关联的潜在疾病。适合鉴别诊断、从多个零散症状推导可能病因。
IDF 加权压制高频常见症状的噪声，让罕见鉴别性症状主导推理方向。
可按实体类型过滤结果（如只返回疾病类）。
输入: {seed_entities: List[str], top_k: int, filter_types: Optional[List[str]]}。
返回: 按相关性排序的关联实体列表（含 PPR 分数和实体类型）。
```

注意：描述中**不绑定具体疾病例子**（如"头痛+发烧+颈强直→脑膜炎"），因为查库确认过真实 KG 里
"头痛"没连任何脑膜疾病（未归一化），这个例子在真实 KG 上跑不通。

### 诊断 3：Memory 噪声 bug

**现象**：抽查 5 条 hard 题，发现 episodic memory 注入了来自前面评测 item 的噪声——
如 item-3（糖尿病视网膜病变）跑完后，chronic_diseases 写入了"糖尿病并发症、糖尿病神经病变"等，
后面不相关的 item 被注入了这些噪声。

**根因**：`eval_cmb_clin.jsonl` 全部 77 条硬编码 `user_id="eval_user"`，
`run_eval.py` fallback 到 `"eval_user"`。所有 item 共享同一个 episodic memory 通道。
orchestrator 的三处 memory_injection（冷启动注入、异步检索、回写新 episode）均以 `user_query.user_id` 为索引。

**后果**：
- 第 N 条 item 完成后，诊断/症状回写到 `"eval_user"` 的 episodic
- 第 N+1 条 item 开始时，冷启动注入读取 `"eval_user"` 全部历史，把不相关慢性病注入 Working Memory
- 随评测推进噪声累积，越后面的 item 噪声越重

**修复**：`run_eval.py` 和 `run_ablation.py` 改为 `user_id=f"eval_{item.item_id}"`，
每条评测 item 用独立 user_id，彻底隔离 episodic memory。

### 面试素材

「全量评测后发现 PPR 调用率只有 6.5%。做了三层诊断：一是统计全部 77 条的工具分布，
发现 93.5% 的题只触发了 NER+local_search；二是分析 Planner prompt，定位到两个根因——
PPR 原描述是一句英文让 8B 模型无法理解，以及 Planner 把 93.5% 的鉴别诊断题判为 medium
而不是 high 导致不触发 PPR；三是发现评测脚本所有题共享同一个 user_id，
episodic memory 跨 item 污染，修复后每条用独立 user_id。
改完 PPR 描述后调用率没变——证明描述不是唯一瓶颈，复杂度判断才是真正卡点。」

### 真实发现分析

**1. PPR 调用率不变 (6.5%)**

改完 PPR 描述后调用率没变——同样的 5 条 high complexity item 调用了 PPR。
**瓶颈不在工具描述，而在 Planner 的复杂度判断**。
93.5% 的临床诊断题被判为 medium（只触发 NER+local_search），不触发 PPR。
LLM 的 complexity 评分逻辑没变，所以工具选择没变。

**2. Top-3 整体不变，但内部结构剧变**

整体 Top-3 loose 不变 (42.1%)，但 **medium 题 +8.4pp，hard 题 -7.5pp**。
这是 memory 噪声消除的效果：
- V1 中前面 item 的慢性病（糖尿病、高血压等）被注入后面 item 的 Working Memory。
  对 medium 题：噪声碰巧提供了一些内科关键词，有时有帮助有时有害，净效果 +8.4pp
  说明 V1 中噪声对 medium 题**实际上是负面的**——消除后回升。
- 对 hard 题：噪声稀释了真正需要的信号，V1 中某些 hard 题"碰巧命中"靠的是噪声里的通用内科词。
  消除后 hard 题**回归真实水平**，下降 7.5pp 是诚实暴露了系统在 hard 题上的真实短板。

**3. 延迟降低 19%，token 减少 34%**

memory 噪声消除的直接后果：V1 中 episodic 注入大量不相关慢性病历史，
塞进 Planner 上下文（working_memory 和 episodic_hints），导致输入变长 → LLM 生成更多 token → 延迟增加。
V2 消除噪声后上下文干净，token 和延迟自然下降。

**4. L3 验证首次出现 (1.3%)**

V1 中 L3 从未触发 (0%)。V2 出现了 1 条 L3。
噪声注入可能也影响了 GradedVerifier 的判定——V1 中更多 L1 规则触发（6.6% vs 1.3%），
因为噪声慢性病触发了过敏/年龄等 L1 规则检查。
